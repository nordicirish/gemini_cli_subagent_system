## 1. Executive Summary

Stage 1.5-D establishes an isolated, deterministic, non-destructive **offline legacy JSON migration and parity verification subsystem** for GEM's SQLite Single Source of Truth (SSoT) program. 

Stage 1.5-C provided the forward SQLite-to-JSON projection capability (`SSoTProjectionGenerator`). Stage 1.5-D completes the loop by verifying whether legacy JSON state files can be parsed, validated, imported into a disposable SQLite database, and projected back to JSON without semantic drift, financial precision loss, or structural corruption.

### 1.1 Core Deliverables Delivered
1. **Migration Domain Models & Exceptions (`python/database/migration/models.py`):** Codified strict exception hierarchies (`MigrationError`, `MigrationSafetyError`, `MigrationValidationError`, `MigrationConflictError`) and structured data classes (`MigrationSource`, `MigrationPlan`, `MigrationResult`, `ParityDiscrepancy`, `ParitySummary`, `ParityResult`).
2. **Versioned Migration Contract (`python/database/migration/contract.py`):** Specified Contract Version 1.0 establishing exact field mappings, Decimal parsing (zero float tolerance), ISO-8601 UTC timestamp enforcement, uppercase ticker normalization, destination validation fail-closed against production paths, and codified rule directive extraction.
3. **Atomic Legacy Importer (`python/database/migration/importer.py`):** Implemented `LegacyJsonImporter`, providing two-phase migration planning and execution: in-memory schema validation and entity extraction followed by atomic execution within a single `UnitOfWork` transaction under explicit `System` role attribution.
4. **Semantic Parity Verifier (`python/database/migration/parity.py`):** Implemented `SSoTParityVerifier`, providing domain-by-domain semantic comparison between legacy state and SQLite projections generated by `SSoTProjectionGenerator`. Explicitly distinguishes exact matches, canonical Decimal scale differences (`equivalent_values`), expected external sections, financial mismatches, missing/unexpected records, and legacy ambiguities.
5. **Comprehensive Automated Test Suite (`tests/test_database_migration.py`):** Authored 46 comprehensive unit, integration, atomicity, idempotency, safety, and dry-run tests covering synthetic fixtures and all actual repository legacy files.
6. **Strict Production Safety & Immutability:** Maintained 100% SHA-256 byte-for-byte invariance across all 8 authoritative repository files (`context/ssot.json`, `context/trade_lessons.json`, `context/decision_log.json`, `context/config.json`, `context/user_config.json`, `context/agent_logs/agent-events.jsonl`, `config.json`, `gem_trading_rules/rules.md`). Confirmed production databases (`context/gem.db`, `cache/market_data.db`) remained absent throughout.
7. **Regression-Free Verification:** Full repository test suite passed with 597 tests (596 passed, 1 skipped platform POSIX test on Windows), `pip check` clean, and complete byte-compilation without warnings.

## 4. Implementation Architecture

The subsystem is implemented within the `python/database/migration/` package:

```
python/database/migration/
├── __init__.py          # Public API exports
├── contract.py          # Validation rules, constants, type parsers, destination validator
├── models.py            # Dataclasses, exceptions, DiscrepancyType enum
├── importer.py          # LegacyJsonImporter (planning, source loading, atomic UnitOfWork import)
└── parity.py            # SSoTParityVerifier (domain-by-domain semantic parity verification)
```

### 4.1 Importer Two-Phase Workflow (`LegacyJsonImporter`)
1. **Source Loading & Type Validation:**
   - Validates input format (accepts single `MigrationSource`, `Path`, `str`, source dict, or sequence thereof).
   - Rejects non-string dictionary keys recursively via `_validate_json_dict_keys()`.
   - Computes SHA-256 fingerprint for all loaded files.
2. **Phase 1: In-Memory Migration Planning (`plan_migration`):**
   - Extracts records across all 6 SQLite domains.
   - Converts numeric values to exact `Decimal` using `parse_financial_decimal` (enforcing maximum scale, rejecting binary float inputs).
   - Normalizes tickers and timestamps.
   - Detects intra-file duplicate keys (e.g. duplicate positions or duplicate cash currencies) and classifies them into `plan.discrepancies` without modifying database state.
   - Identifies externally managed sections (`state_context`, `runtime_flags`, etc.) and records them in `plan.external_sections`.
3. **Phase 2: Atomic Execution (`import_into`):**
   - Validates destination database safety.
   - Enters `execution_role_context("System")` to authorize financial mutations.
   - Opens an atomic `UnitOfWork(db_mgr)` transaction.
   - Verifies existing records for idempotency:
     - Identical records are safely skipped (`skipped_counts` incremented).
     - Conflicting records raise `MigrationConflictError`, triggering a fail-closed transaction rollback.
   - Calls repository upsert methods:
     - `uow.cash.set_cash_balance(...)`
     - `uow.positions.upsert_position(...)`
     - `uow.watchlist.upsert_watchlist_item(...)`
     - `uow.scout_categories.upsert_category(...)`
     - `uow.trade_lessons.upsert_lesson(...)`
     - `uow.decision_log.append_entry(...)`
   - Commits atomically on completion. In the event of an error, rolls back completely, leaving the database unmodified.

### 4.2 Parity Verifier (`SSoTParityVerifier`)
`SSoTParityVerifier` takes legacy sources and a fresh projection generated by `SSoTProjectionGenerator`:
1. Consolidates legacy state.
2. Evaluates domain by domain using exact Decimal comparison:
   - **Exact Matches (`exact_matches`):** Raw value, type, and string representation are identical.
   - **Equivalent Values (`equivalent_values`):** Values are mathematically equivalent via `Decimal` comparison, but representation differs (e.g. legacy integer `10` or float `500.0` vs canonical string `"10"` or `"500.0"`).
   - **Expected External Sections (`expected_external_sections`):** Sections managed outside SQLite (e.g. `_projection_metadata`, `state_context`).
   - **Financial Mismatches (`financial_mismatches`):** Genuine discrepancies where `Decimal(leg) != Decimal(proj)`.
   - **Missing Records (`missing_records`):** Record exists in legacy source but was not projected from SQLite.
   - **Unexpected Records (`unexpected_records`):** Record exists in SQLite projection but was absent from legacy input.
   - **Unresolved (`unresolved`):** Malformed entries that could not be parsed.
3. Sorts all discrepancies deterministically by domain and path.
